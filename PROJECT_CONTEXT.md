## 1. Report-ready project description

CloudPilot is a CPU right-sizing simulator and workload replay tool. It compares five supervised demand regressors and four heuristic allocation policies using synthetic or uploaded CPU time series. It trains models per run, calibrates policy margins on validation data, compares held-out allocations with a static CPU reservation, and reports operational violation, capacity savings, utilization, wastage, prediction errors and hypothesis results. The web application exposes the simulator, a static study report and anonymous visitor-scoped run history. Render, Vercel and Supabase are the configured deployment components. The repository contains no cloud actuator, scheduler, autoscaler, telemetry collector, cluster inventory, trained-model artifact or billing integration. Its measured “savings” are simulated CPU reservation reductions. Memory, network, storage, IOPS, latency, financial savings and real-world SLA attainment were outside the verified evaluation. Sources: [README](README.md#L5), [methodology](docs/method.md#L59), [engine](backend/app/engine/runner.py#L261), [frontend routes](frontend/src/App.tsx#L13), [deployment guide](docs/DEPLOY.md#L1).

## 2. Backend, persistence and security

### HTTP interfaces

- Public `GET /health` reports process liveness. `GET /ready` validates config and probes the selected repository. The application factory validates configuration before serving. Protected `GET /api/ping` is an authentication diagnostic. `GET /api/methods` returns the nine method descriptors. `GET /api/limits` exposes configured size/time limits and a 50-run history limit. - `POST /api/simulate` defaults to seed 42, 8 services, 600 steps and 1% validation violation. Request validation allows at least 2 services, at least 388 steps and target violation from 0.5% through 5%. Configured defaults cap runs at 20 services and 1,000 steps. `POST /api/simulate/csv` accepts multipart CSV and the same target range, uses fixed seed 42 in the returned metadata and runs the same pipeline. Both routes offload computation to a thread, apply per-client concurrency and global rate limits, and return parameters, split results, hypothesis verdicts, elapsed time and persistence status. The browser proxy allows limits, methods, run list/detail/delete and both simulations. The backend health, readiness and ping endpoints are outside that allowlist. ### Database and data handling

- One SQL migration defines `public.simulation_runs` with UUID `id` defaulting to `gen_random_uuid()`, `created_at` as timestamp with time zone defaulting to `now()`, required text `client_id`, source constrained to `simulated|csv`, required JSONB `params`, status constrained to `ok|error`, and nullable JSONB `result`, text `error` and integer `duration_ms`. Production validation requires both settings and HTTPS for the URL. An outage produces an unhealthy readiness probe or failed persistence, with no runtime switch to memory. Successful simulations insert the result and attempt to prune older rows beyond the newest 50 per client. CSV bytes and filenames are omitted. Derived per-service totals, allocation metrics and request metadata are present in JSON results. No automatic expiry across inactive visitors is defined. The migration can represent errors but these API paths persist successful simulations only. ### Security controls and residual issues

- Protected requests use constant-time shared-key comparison. Production requires a key of at least 32 characters, configured origin settings without a wildcard, and Supabase configuration. Development can explicitly bypass auth. The proxy injects the server-side key and visitor ID from a UUIDv4 `cp_vid` cookie, created with Secure, HttpOnly, SameSite=Lax, path / and one-year max age. History ownership derives from SHA-256 of the key and visitor UUID, or a truncated key hash for direct calls without a visitor header. This is anonymous bearer scoping with no user account. Cookie loss or API key rotation changes access to historical records. The cookie is syntax-validated and unsigned, so possession of its value is the security boundary. [Settings](backend/app/config.py#L40) · [Authentication](backend/app/security.py#L28) · [Cookie and origin checks](frontend/api/_proxyHelper.ts#L119).
- The proxy checks URL and route, restricts query parameters, applies origin checks when supplied, controls upstream headers, sets no-store, and applies content type and nominal 5.5 MiB size rules. Backend middleware supplies request IDs, CORS allowlisting, structured JSON logging with credential masking, and security headers on the normal response path. Backend Content-Length cap defaults to 1 MiB, with 5 MiB for multipart CSV, and the CSV handler also checks file bytes. The 5 MiB multipart cap includes overhead, so the effective file maximum is lower for requests with declared lengths. The proxy accumulates body chunks even after it detects the limit and backend middleware relies on a declared length, so these are incomplete streaming memory bounds. API simulation failures interpolate exception text in HTTP 500 responses. [Proxy body reader](frontend/api/%5B...path%5D.ts#L14) · [Proxy validation](frontend/api/_proxyHelper.ts#L15) · [Middleware](backend/app/main.py#L64) · [Logging](backend/app/logging_setup.py#L20) · [Route failures](backend/app/routes/simulate.py#L212).
- Sliding 60-second windows default to 30 API requests per client and 20 simulation starts across clients per process, with a one-active-simulation gate per client. Rate state and the gate are in-process, so they reset on restart and are unshared between replicas. The rate limiter retains client map entries until reset and only prunes timestamps for the requesting client. The global rate cap counts starts and there is no global concurrent-job limit or persistent queue. Because thread work is cooperative, a running model fit can outlive an HTTP timeout and the gate may already have been released. [Limiters](backend/app/ratelimit.py#L17) · [Concurrency gate](backend/app/routes/simulate.py#L25) · [Timeout wrapper](backend/app/routes/simulate.py#L158) · [Stage deadline](backend/app/engine/runner.py#L25).
- Insert and prune are separate operations, and the HTTP repository retries transient requests, including inserts, without an application-level idempotency key. A committed insert followed by an ambiguous network failure can yield duplicates. A pruning exception can return `saved=false` with an existing `run_id`. [Repository retry](backend/app/db/repository.py#L182) · [Insert](backend/app/db/repository.py#L230) · [Route write path](backend/app/routes/simulate.py#L180).

## 3. Simulator, allocation and mathematical definitions

### Workload and features

- Synthetic arrays are service-major with five-minute steps, 288 per day and 2,016 per week. Seeded NumPy RNG creates service IDs and assigns four round-robin metadata groups. It selects `ceil(0.30 N)` hard services without replacement. For service base `b ~ U(2,32)` cores, pre-floor demand is `b + b*d*sin(2πt/288 + φ) + b*w*sin(2πt/2016) + b*g*t/T + ε + shifts + bursts`, with `d ~ U(.20,.40)`, `w ~ U(.10,.25)`, `φ ~ U(0,2π)`, `g ~ U(-.10,.15)` and independent Gaussian noise of SD `0.08b` or `0.25b` for hard services. Hard traces longer than 100 steps receive 1–3 changes. Each sorted change multiplies a cumulative factor initially 1 by a draw from `U(.65,1.50)` and adds `0.5b(factor−1)` to the remaining tail. Each interval independently starts a burst with probability .01 standard or .04 hard, adding `b*U(1.5,3.5)` for 2–6 steps, clipped at the end. Overlaps accumulate. Final demand is floored at 0.05 cores. Static reference is `max(1.30 × P99(full trace), 1.05 × peak(full trace))`. [Generator](backend/app/engine/generator.py#L9) · [Generator equations](backend/app/engine/generator.py#L57).
- CSV is UTF-8 with case/space-normalized columns `service_id,timestamp,cpu_demand`. Nonempty IDs/timestamps and nonnegative numeric demand are expected. The parser sorts service IDs and orders each service by timestamp string, truncates to the minimum row count, floors values at .01 cores, and sets static request to 1.30 times each retained trace peak. There is no typed timestamp conversion, cadence normalization, duplicate check or cross-service time alignment. Numeric strings are ordered lexically. Nonfinite float values can pass the negative-value check and fail downstream. [CSV parser](backend/app/engine/csv_loader.py#L17).
- Target is observed CPU demand at step `t`. The 14 inputs are demand at lags 1, 2, 3, 6, 12 and 288, mean/max/population SD over each of `[t−12,t)` and `[t−48,t)`, and sine/cosine of `2π(t mod 288)/288`. The feature matrix and all targets, service indices, time indices and allocations share service-major ordering. Service ID, group and hard flag are omitted from model inputs. Walk-forward predictions use observed demand from earlier evaluation intervals as it becomes available. [Features](backend/app/engine/features.py#L7) · [Canonical layout](backend/app/engine/features.py#L70) · [Evaluation assembly](backend/app/engine/runner.py#L53).

### Models and baselines

All five models are fitted from scratch per split. Above 200,000 training rows the code samples 200,000 uniformly without replacement with seed 42. Fixed stochastic model seed is 42. The offline CLI can override tree counts for RF, GB and GBR. [Model factory](backend/app/engine/models.py#L12) · [Fitting](backend/app/engine/models.py#L55).

- **LR:** scikit-learn ordinary least squares, minimizing squared residuals for a linear predictor with an intercept.
- **DT:** regression tree with depth at most 8 and minimum leaf size 20.
- **RF:** 100 regression trees, depth at most 12, minimum leaf size 20, `n_jobs=-1`. Predictions average trees.
- **GB:** 200 gradient boosting trees, squared-error loss, depth 3, learning rate .05, subsample .8.
- **GBR_q95:** same boosting hyperparameters with quantile loss at .95. For residual `u = D−prediction`, pinball loss is `max(.95u, −.05u)`.
- **Static:** constant allocation `S_i` for each service.
- **Rolling max:** `max(D_i[t−48:t])`, the preceding four hours.
- **Rolling p99:** 99th percentile of `D_i[max(0,t−2016):t]`, with at least one day of preceding observations.
- **EWMA:** `E_0 = D_0`, `E_t = αD_t + (1−α)E_{t−1}`, raw allocation `E_{t−1}`. It tries `α ∈ {.1,.2,.3,.5}` and picks the feasible alpha/margin combination with highest validation savings. If all fail it uses the first alpha and no margin for test diagnostics. [Baseline implementations](backend/app/engine/baselines.py#L9).

### Splits, calibration and evaluation

- **TIME** uses all services and half-open ranges `[288, floor(.60T))`, `[floor(.60T), floor(.75T))`, and `[floor(.75T),T)` for training, validation and testing. In the study the boundaries are 288, 2,419, 3,024 and 4,032, yielding 426,200 training rows before the sampling cap, 121,000 validation rows and 201,600 test rows per seed.
- **SERVICE** uses array order and first `max(1,floor(.60N))` services for training, next `max(1,floor(.15N))` for validation, and remaining for testing. Each uses `[288,T)`. The study has 120, 30 and 50 services, or 449,280 training rows before sampling, 112,320 validation rows and 187,200 test rows per seed. Held-out services still require their own observed history. Small-fleet fallback can compromise disjointness. [Both splits](backend/app/engine/runner.py#L281).
- For raw prediction `P`, multiplicative allocation is `A=mP`, `m=1.00…1.60` by .01. Additive allocation is `A=P+(q/100)S_i`, `q=0…30` in .5 pp increments. The code checks all multiplicative candidates in ascending order first, then additive candidates in ascending order, stopping at the first feasible candidate. This is ordering by grid, with no joint comparison of overhead across families. GBR checks the raw forecast first as a special case. Static keeps multiplier 1.00. Baseline comparator is the validation-feasible policy with greatest validation savings, with annotated static fallback if none qualify. Test policies retain the validation margin unchanged. [Margin code](backend/app/engine/margins.py#L15) · [Baseline and ML selection](backend/app/engine/runner.py#L93) · [Test evaluation](backend/app/engine/runner.py#L208).
- With demand `D`, allocated CPU `A`, static reservation `S` and raw prediction `P`, pooling all service-time rows gives violation `mean(D>A)`, savings `1−ΣA/ΣS`, utilization `ΣD/ΣA`, wastage `Σmax(A−D,0)/ΣA`, MAE `mean(|P−D|)`, and RMSE `√mean((P−D)²)`. Reported ratios use zero guards for nonpositive denominators. Utilization represents demand over allocation and can exceed 100%. Utilization plus wastage need not equal 100% when demand is unmet. The evaluator also sums demand, allocation and static reservation per service. Infeasible policies return public savings/utilization/wastage fields of zero, while violation, raw forecast errors and per-service accounting remain empirical. [Metrics](backend/app/engine/evaluate.py#L76) · [Infeasible presentation](backend/app/engine/runner.py#L216).
- Hypothesis effect is GBR minus comparator in pooled savings, equivalent to `(ΣA_comparator−ΣA_GBR)/ΣS`. The paired bootstrap draws the same service indices for both methods with replacement, retains each service's full evaluated interval, uses 10,000 resamples and seed 42, and uses the 2.5th and 97.5th percentiles. The code reports twice the empirical opposite-sign tail fraction, clipped to 1. Estimates of zero tail hits can produce numeric p=0 and the report formats that as `p < 0.0001`. This is an empirical zero-effect diagnostic, including for H2 where the verdict instead uses a −1 pp bound. H1 requires validation-feasible GBR and lower bound >0 pp. H2 requires validation-feasible GBR and lower bound >−1 pp. H3 checks whether both observed GBR test violations are ≤1.5%. [Bootstrap](backend/app/engine/bootstrap.py#L26) · [H1](backend/app/engine/runner.py#L314) · [H2/H3](backend/app/engine/runner.py#L366).

## 5. Audit findings and documentation discrepancies

1. **Full-trace reference weakens the blanket no-leakage claim.** Lag/rolling features and raw dynamic baseline forecasts are causal. However, both loaders compute static capacity using held-out demand, and additive allocations use that capacity even during calibration and testing. The absolute savings and additive-policy rankings are conditional on this hindsight-informed reference. The methodology describes historical P99 alone and claims only prior observations determine allocations. The CPU-only and synthetic-data limitations remain applicable. [Methodology](docs/method.md#L16) · [Causality claim](docs/method.md#L38) · [Synthetic static reference](backend/app/engine/generator.py#L123) · [CSV static reference](backend/app/engine/csv_loader.py#L104) · [Additive application](backend/app/engine/margins.py#L20).
2. **Accepted input range includes unsimulatable workloads.** The TIME training range is empty for any horizon below 482 because `floor(.60T)` must exceed 288. The synthetic API accepts 388–481 steps and the CSV parser accepts a shortest trace of 300 or more. These can lead to HTTP 500 rather than validation errors. A one-service CSV leaves validation empty, while a successful two-service run reuses the second service for validation and testing. Negative synthetic seeds are typed as integers without a lower bound and NumPy rejects them downstream. [Request validation](backend/app/routes/simulate.py#L47) · [Parser minimum](backend/app/engine/csv_loader.py#L13) · [Engine splits](backend/app/engine/runner.py#L281) · [Empty training handling](backend/app/engine/models.py#L55).
3. **CSV chronology depends on input representation.** Timestamp ordering is lexical per service, intervals and timestamps are assumed aligned after truncation, and no finite-number validation is present. Consequently “five minutes” is a property of correctly prepared data, and position-based alignment can compare noncontemporaneous observations. [Parser](backend/app/engine/csv_loader.py#L55).
4. **Feasibility and inference language needs precision.** The study plan's statement about infeasibility “on validation or test” conflicts with the corrected implementation of H1/H2, which uses validation feasibility and separate test CI decisions. An infeasible comparator is annotated and does not automatically change the H1/H2 decision. H3 checks observed violations alone. The bootstrap's reported p-value is tested against zero, including on SERVICE. The report's per-seed validation cells print bounds rather than recorded exact values. [Study plan](docs/study_plan.md#L29) · [Runner](backend/app/engine/runner.py#L314) · [D2/D5/D6](docs/deviations.md#L23) · [Results](docs/results.md#L84).
5. **Margin and row-alignment claims are stronger than the checks.** “Smallest margin” means first feasible within ordered families, with multiplicative precedence over additive. The evaluator checks vector shapes and index lengths but does not independently verify the ordering of each allocation vector. The corrected runner and dataset builder establish service-major ordering by construction. No nonnegative clipping is applied to regressor outputs or final allocations. [Margin search](backend/app/engine/margins.py#L61) · [Evaluator checks](backend/app/engine/evaluate.py#L52) · [Dataset construction](backend/app/engine/features.py#L108) · [Prediction and allocation](backend/app/engine/runner.py#L177).
6. **Integration gaps.** Direct Vite development routing adds neither an API key nor visitor scoping. A key-required local backend can reject SPA actions unless an authenticated proxy is used or the developer enables the development bypass. The fallback UI declares history limit 100 while backend reports/prunes to 50. Production proxy runtime and backend request timeout share the same nominal 55-second upper budget before accounting for network delay or database writes. There is no documented production measurement of these delays. [Vite config](frontend/vite.config.ts#L5) · [Simulate UI fallback](frontend/src/pages/SimulatePage.tsx#L8) · [Upload UI fallback](frontend/src/pages/UploadPage.tsx#L8) · [Limits](backend/app/routes/limits.py#L25) · [Backend wrapper](backend/app/routes/simulate.py#L165) · [Deployment guide](docs/DEPLOY.md#L73).
7. **Study run artifacts have different availability.** A clean clone has the aggregate, but seed files are ignored and required for report-only regeneration. The local presence of those files is specific to this workspace. The invalid v1 results and obsolete composite headline wording in the deviations appendix should not be used as corrected headline results.
