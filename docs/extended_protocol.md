# Extended experiment protocol (extended-v1)

This protocol is separate from the published CPU-only benchmark. H1–H3 and their results belong to the CPU-only benchmark. Its static reservation can use full-trace peaks and appears in both the savings denominator and the additive margin scale. Extended-v1 uses a fixed reservation per service based on 1.3 times the maximum of that service's first 288 five-minute observations, with a positive floor. This prefix is available before any scored row, including for unseen services. It is local provisioning history, not supervised training data for those services. Future demand is never used to size the reference.

## Evaluation

- TIME is a chronological 60/15/25 split after excluding the fixed warm-up prefix from scoring and supervised rows. SERVICE uses the existing deterministic disjoint 60/15/25 service partition, with the same warm-up requirement. Forecasts use histories strictly before the scored step.
- CPU and GiB are fitted independently. Use the existing five estimators, baselines and margin grids. Select margins only on validation. Clamp negative predictions to zero for allocation and margin selection while scoring unmodified forecasts. Prediction MAE and RMSE are in resource units; MSE is in squared units. Savings use the resource's causal static reference. Utilization is total demand divided by capacity, and wastage is unused capacity divided by total capacity. These are workload allocation metrics; scheduler processing is tracked separately.
- Joint validation feasibility requires a valid allocation for both resources and a validation fraction of rows with either resource under-allocated at or below the common target. The held-out joint violation rate also counts the union. Keep the predetermined static reference as a task comparator even if it misses the validation target. Schedule dynamic policies only when jointly feasible. Raw prediction errors remain reportable for infeasible predictors.
- Synthetic memory includes a service-specific resident set, daily and weekly variation, correlated CPU activity, random noise, bursts and longer-lived pressure. CSV mode requires a shared, uniformly spaced five-minute timestamp grid and pairs both resources per observation.
- One task arrives per service per evaluated interval at the interval boundary. A seeded task mix assigns CPU work around the observed CPU demand multiplied by 300 seconds and assigns memory as a seeded fraction of demand. These are simulated offerings produced from the workload and shared across policies, not training features or measured traces.
- Each service has its own finite FIFO waiting queue and admitted set (32 tasks each) and admits its head when memory fits. Running tasks share the service CPU capacity equally. Completions are calculated continuously within each fixed-capacity interval, releasing memory immediately. At an interval boundary, tasks that cannot fit are suspended, with earlier starts given priority. Suspended work resumes before new admissions and retains its accumulated progress. A full queue rejects new arrivals. No work is shared between services. Each held-out evaluation starts empty and stops at the final interval without draining.
- Waiting means arrival to first memory admission. Time to first service means arrival to first positive CPU progress. Response means arrival to completion. Execution duration means completion minus admission and includes suspensions. Completion-only statistics are reported alongside unfinished, queued, suspended and rejected counts. Throughput is completions divided by elapsed simulated seconds. Backlog counts waiting plus suspended tasks.
- Pilot uses seed 42, 4 services, 600 intervals, 1% target and default estimator parameters. A full offline study is pre-specified for seeds 1–10, 200 services, 4,032 intervals and 1% target with default estimators. Check resource requirements before running the full study. Report per-seed results and compare only policies on the same split and offered tasks. The pilot does not establish superiority or validate production latency.
- Online execution is local development opt-in only, with existing request budgets and explicit workload caps. Larger runs use the offline CLI. Store bounded diagnostics and task samples, never raw uploads.
